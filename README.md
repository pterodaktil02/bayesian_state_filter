# Bayesian State Filter for Home Assistant

Версия: **0.2.1.6**

[English README](README.en.md)

> **Не путать со встроенной интеграцией Home Assistant [`bayesian`](https://www.home-assistant.io/integrations/bayesian/).** Встроенная интеграция решает другую задачу: по набору наблюдений она оценивает вероятность события и создает **бинарный** сенсор `on/off`. Даже если среди наблюдений используются числовые состояния, результатом остается `binary_sensor`. `bayesian_state_filter` предназначен именно для **числовых сенсоров и непрерывных величин**: он объединяет несколько асинхронных измерений одной физической величины и выдает непрерывную числовую оценку — например температуры, влажности или давления.

`bayesian_state_filter` — пользовательская интеграция Home Assistant для байесовского объединения нескольких асинхронных числовых сенсоров в одну устойчивую оценку общего скрытого состояния.

Интеграция не просто усредняет датчики. Она учитывает:

- постоянные относительные смещения источников (`bias`);
- разную фактическую ошибку наблюдения (`sigma`);
- различную частоту обновления;
- асинхронность измерений;
- выбросы и временно "уехавшие" источники;
- динамику самого измеряемого процесса;
- историю Recorder до перезапуска Home Assistant.

Типичный пример — несколько датчиков температуры в одной комнате. Однако компонент не привязан к температуре и может использоваться с любыми числовыми источниками, если они измеряют одну и ту же физическую величину в совместимых единицах.

> Важно: интеграция **не преобразует единицы измерения**. Все источники одного экземпляра фильтра должны быть совместимы по физическому смыслу и масштабу.

---

## 1. Как устроен фильтр

Внутреннее состояние двумерное:

```text
x[0] = уровень процесса
x[1] = локальная скорость изменения
```

Для каждого нового измерения выполняется отдельное байесовское обновление. Источники заранее не сводятся к одному среднему значению.

Модель скорости затухающая:

```text
dx/dt = v
dv/dt = -v/tau + process_noise
```

Здесь `tau` внутренней модели скорости — это **время памяти локального тренда**, а не физическая постоянная времени объекта.

Отдельно оценивается `characteristic_time_s` — характерное время изменения **уровня процесса**, получаемое по робастной временной вариограмме. Эти две величины имеют разный физический смысл.

### Робастность к выбросам

Обновление выполняется по распределению Стьюдента (Student-t). Для согласованного измерения вес близок к 1. Для выброса вес плавно уменьшается.

При `student_nu = 4` вес приближенно равен:

```text
w = min(1, (nu + 1) / (nu + z^2))
```

где `z` — нормированная инновация.

Например, при `z = 6.6` вес получается около `0.1`, поэтому одно сильно выбивающееся измерение почти не может утянуть итоговую оценку за собой.

## 2. Установка

Скопируйте каталог:

```text
custom_components/bayesian_state_filter
```

в:

```text
/config/custom_components/bayesian_state_filter
```

После установки или обновления выполните **полный перезапуск Home Assistant**.

В версии 0.2.1.6 интеграция настраивается через YAML как сенсорная платформа. Настройка через интерфейс Home Assistant (Config Flow) пока не реализована.

---

## 3. Минимальная конфигурация

```yaml
sensor:
  - platform: bayesian_state_filter
    name: "Температура зала"
    ensemble:
      sources:
        - sensor.temperature_1
        - sensor.temperature_2
        - sensor.temperature_3
```

При такой конфигурации используются все значения по умолчанию.

Если `sensor:` подключается через `!include_dir_merge_list`, файл может начинаться сразу с элемента списка:

```yaml
- platform: bayesian_state_filter
  name: "Температура зала"
  ensemble:
    sources:
      - sensor.temperature_1
      - sensor.temperature_2
      - sensor.temperature_3
```

---

## 4. Рекомендуемая конфигурация

```yaml
sensor:
  - platform: bayesian_state_filter
    name: "Температура зала"

    ensemble:
      sources:
        - sensor.temperature_1
        - sensor.temperature_2
        - sensor.temperature_3
        - sensor.temperature_4
      min_sources: 2

    bayes:
      noise_model: auto
      history_days: 7
      save_every_s: 60
      tau_points: 16
      characteristic_refit_s: 1800
      student_nu: 4
      diagnostics: compact
```

Для большинства задач этого достаточно.

# 5. Полный справочник конфигурации

## 5.1 Верхний уровень

| Параметр | Тип | По умолчанию | Допустимые значения | Назначение |
|---|---|---|---|---|
| `platform` | строка | — | `bayesian_state_filter` | Имя платформы сенсора. Обязательный параметр Home Assistant. |
| `name` | строка | `Bayesian Sensor` | любая строка | Имя создаваемого сенсора. |
| `ensemble` | блок YAML | `{}` | см. ниже | Набор исходных сенсоров. |
| `bayes` | блок YAML | `{}` | см. ниже | Параметры обучения, динамики, модели шума и диагностики. |

## 5.2 `ensemble`

### `ensemble.sources`

```yaml
ensemble:
  sources:
    - sensor.temperature_1
    - sensor.temperature_2
```

**Тип:** список `entity_id`.

Практически обязательный параметр. Пустой список синтаксически допустим, но фильтр не получит ни одного измерения и работать не сможет.

Источники должны:

- иметь числовое состояние;
- измерять одну и ту же физическую величину;
- использовать совместимые единицы;
- иметь общий смысл скрытого состояния.

Состояния `unknown`, `unavailable`, `None`, нечисловые и не конечные значения игнорируются.

Метаданные итогового сенсора (`unit_of_measurement`, `device_class`, `state_class`, `icon`) наследуются от первого пригодного источника.

### `ensemble.min_sources`

```yaml
ensemble:
  min_sources: 2
```

**Тип:** целое число  
**По умолчанию:** `1`  
**Минимум:** `1`

Минимальное число **свежих** источников, необходимое для обработки нового измерения.

Источник считается свежим примерно в течение:

```text
max(3 * median_dt_source,
    0.20 * characteristic_time_or_velocity_tau,
    300 s)
```

Если свежих источников меньше `min_sources`, измерение сохраняется для накопления истории, но основное байесовское обновление не выполняется.

Практически:

- `1` — максимальная доступность;
- `2` — разумный вариант для многосенсорной температуры;
- `3+` — имеет смысл только при большом числе источников.

## 5.3 Блок `bayes`

Все параметры ниже находятся внутри `bayes:`.

### `bayes.noise_model`

```yaml
bayes:
  noise_model: auto
```

**Тип:** строка  
**По умолчанию:** `auto`

Допустимые значения:

| Значение | Поведение в 0.2.1.6 |
|---|---|
| `auto` | Пока консервативно выбирает `gaussian`. Интерфейс подготовлен для будущего автоматического выбора модели. |
| `gaussian` | Для данного источника используется постоянная дисперсия наблюдения `sigma_i^2`. |
| `poisson` | Дисперсия зависит от текущего уровня сигнала. Коэффициент оценивается автоматически. |

Неизвестное значение вызывает предупреждение в журнале и заменяется на `auto`.

Для гауссовской модели:

```text
R_i = sigma_i^2
```

Для пуассоновской модели в текущей реализации:

```text
R_i(y) = k_i * |y|
k_i ~= sigma_i^2 / typical_abs_level_i
```

Пользователь не задает `k` вручную.

> В 0.2.1.6 режим `auto` еще не определяет пуассоновский шум автоматически. Для счетного сигнала `poisson` нужно выбрать явно.

### `bayes.history_days`

```yaml
bayes:
  history_days: 7
```

**Тип:** вещественное число  
**По умолчанию:** `7.0` суток  
**Минимум:** `0.1` суток

Количество истории каждого источника, запрашиваемой из Recorder при запуске.

История используется для:

- оценки относительных смещений `bias`;
- попарной калибровки `sigma`;
- предварительного обучения фильтра;
- оценки характерного времени;
- обучения внутренней модели локальной скорости.

Текущая `sigma` не оценивается по всей истории целиком: используется более свежее окно, чтобы давно прошедшие режимы не портили текущую оценку качества источника.

Практические значения: `1`, `3`, `7`, `14+` суток. Для большинства бытовых процессов рекомендуется `7`.

### `bayes.save_every_s`

```yaml
bayes:
  save_every_s: 60
```

**Тип:** вещественное число  
**По умолчанию:** `60` секунд  
**Минимум:** `5` секунд

Минимальный интервал между сохранениями состояния фильтра в Home Assistant Store.

Сохраняются состояние, ковариация, калибровки источников, обученная динамика, оценка характерного времени и параметры временной сетки.

### `bayes.tau_points`

```yaml
bayes:
  tau_points: 16
```

**Тип:** целое число  
**По умолчанию:** `16`  
**Минимум:** `8`

Количество точек логарифмической сетки внутренней модели локальной скорости. Для обычной телеметрии рекомендуется оставить `16`.

### `bayes.tau_min_s`

```yaml
bayes:
  tau_min_s: 60
```

**Тип:** положительное вещественное число или параметр отсутствует  
**По умолчанию:** определяется автоматически

Нижняя граница `tau` внутренней модели памяти локальной скорости. К `characteristic_time_s` напрямую не относится.

Автоматическая нижняя граница приблизительно равна:

```text
max(4 * fused_grid_step,
    4 * fastest_source_median_dt,
    10 s)
```

Нулевое, отрицательное, не конечное или `null` значение означает отсутствие ручной границы.

### `bayes.tau_max_s`

```yaml
bayes:
  tau_max_s: 86400
```

**Тип:** положительное вещественное число или параметр отсутствует  
**По умолчанию:** определяется автоматически

Верхняя граница `tau` внутренней модели локальной скорости.

Автоматическая граница приблизительно равна:

```text
max(8 * auto_tau_min,
    history_span / 2)
```

### `bayes.characteristic_tau_min_s`

```yaml
bayes:
  characteristic_tau_min_s: 300
```

**Тип:** положительное вещественное число или параметр отсутствует  
**По умолчанию:** определяется автоматически

Нижняя граница поиска характерного времени уровня процесса по временной вариограмме.

Поддерживается старый алиас:

```yaml
characteristic_time_min_s: 300
```

Если заданы оба параметра, приоритет у `characteristic_tau_min_s`.

### `bayes.characteristic_tau_max_s`

```yaml
bayes:
  characteristic_tau_max_s: 172800
```

**Тип:** положительное вещественное число или параметр отсутствует  
**По умолчанию:** определяется автоматически

Верхняя граница поиска характерного времени уровня процесса.

Поддерживается старый алиас:

```yaml
characteristic_time_max_s: 172800
```

Если оценка упирается в верхнюю границу, `characteristic_time_status` становится `longer_than_history`, а `characteristic_time_identifiable` — `false`.

### `bayes.characteristic_refit_s`

```yaml
bayes:
  characteristic_refit_s: 1800
```

**Тип:** вещественное число  
**По умолчанию:** `1800` секунд  
**Минимум:** `300` секунд

Минимальный интервал между повторными оценками `characteristic_time_s` во время работы.

### `bayes.forget_time_s`

```yaml
bayes:
  forget_time_s: 259200
```

**Тип:** положительное вещественное число или параметр отсутствует  
**По умолчанию:** определяется автоматически

Время забывания для банка моделей прогнозной динамики, который обучает `velocity_tau` и `process_noise_q`.

Автоматически:

```text
forget_time_s = max(3 days, 8 * tau_max)
```

Для обычного использования лучше оставить автоматический выбор.

### `bayes.student_nu`

```yaml
bayes:
  student_nu: 4
```

**Тип:** вещественное число  
**По умолчанию:** `4.0`  
**Минимум:** `1.01`

Число степеней свободы распределения Стьюдента.

- меньше `nu` — тяжелее хвосты и сильнее подавление больших выбросов;
- больше `nu` — поведение ближе к обычному гауссовскому обновлению;
- `4` — разумный общий вариант.

Робастное обновление включено всегда. Параметр `robust_enable` больше не нужен.

### `bayes.diagnostics`

```yaml
bayes:
  diagnostics: compact
```

**Тип:** строка  
**По умолчанию:** `compact`

Допустимые значения:

| Значение | Результат |
|---|---|
| `compact` | Рекомендуемый набор атрибутов. |
| `full` | Добавляет внутренние исследовательские параметры. |
| `debug` | Алиас `full`. |
| `verbose` | Алиас `full`. |

Любая другая строка фактически ведет себя как `compact`.

# 6. Что происходит при запуске

При полном запуске Home Assistant компонент:

1. Запрашивает историю каждого источника из Recorder.
2. Удаляет некорректные значения.
3. Оценивает типичный интервал обновления `median_dt_s`.
4. Строит общую временную сетку.
5. Оценивает относительный `bias` каждого источника.
6. Получает предварительную оценку характерного времени.
7. Выбирает свежее окно для калибровки `sigma`.
8. Совмещает близкие по времени измерения разных источников.
9. Для пар источников использует приближение:

   ```text
   Var(i - j) ~= sigma_i^2 + sigma_j^2
   ```

10. Решает систему для отдельных `sigma_i` с ограничением неотрицательности и нижней границей идентифицируемости.
11. Перестраивает объединенную историю с обученными дисперсиями источников.
12. Оценивает итоговый `characteristic_time_s`.
13. Обучает внутреннюю модель динамики (`velocity_tau`, `process_noise_q`).
14. Последовательно пропускает объединенную историю через фильтр.
15. Сохраняет обученное состояние в Home Assistant Store.

Если история Recorder недоступна, компонент пытается восстановить сохраненное состояние. Если и его нет, фильтр начинает работу с текущих измерений и обучается по мере накопления данных.

# 7. Что означают `bias` и `sigma`

## `bias`

`bias` — относительное смещение источника относительно общего ансамбля.

```text
corrected = raw - bias
```

Например:

```text
raw       = 23.24
bias      = +0.41
corrected = 22.83
```

Это не абсолютная метрологическая калибровка. Если все датчики одновременно смещены на одинаковую величину, ансамбль без внешнего эталона этого не узнает.

## `sigma`

`source_health.<source>.sigma` — **эффективная ошибка наблюдения общего скрытого состояния**, а не паспортная точность датчика.

В нее могут входить:

- собственный шум сенсора;
- квантование;
- локальный микроклимат;
- инерция корпуса;
- небольшая ошибка временного совмещения;
- остаточная несогласованность источника с общей скрытой величиной.

Поэтому датчик с паспортной точностью `+-0.1 C` вполне может иметь `sigma = 0.25 C`, если его точка установки систематически живет немного своей жизнью относительно остального помещения.

### Попарная калибровка

Для двух близких по времени измерений общая динамика процесса в первом приближении сокращается:

```text
Var(sensor_i - sensor_j) ~= sigma_i^2 + sigma_j^2
```

Для нескольких источников получается переопределенная система попарных сравнений. Нижняя граница дисперсии не дает оценке `sigma` численно схлопнуться к нулю при слабой идентифицируемости.

# 8. Характерное время процесса

Для уровня процесса используется робастная временная полувариограмма:

```text
gamma(h) = nugget + process_variance * (1 - exp(-h / tau))
```

где:

- `nugget` — высокочастотный и измерительный вклад;
- `process_variance` — амплитуда движения скрытого процесса;
- `tau` — характерное время уровня.

Это характеристика наблюдаемых данных, а не обязательно чистая физическая постоянная времени объекта.

Возможные `characteristic_time_status`:

| Статус | Смысл |
|---|---|
| `identified` | Характерное время различимо по имеющимся данным. |
| `insufficient_signal` | Изменение уровня слишком мало относительно шума. |
| `below_resolution` | Характерное время ниже временного разрешения данных или нижней границы поиска. |
| `longer_than_history` | Процесс медленнее доступного диапазона истории. |
| `uncertain` | Оценка есть, но критерии уверенной идентификации не выполнены. |
| `unavailable` | Оценка еще не построена. |

`characteristic_time_identifiable: true` — главный признак того, что `characteristic_time_s` можно интерпретировать как действительно идентифицированную величину.

# 9. Основные диагностические атрибуты

При `diagnostics: compact` публикуются основные рабочие атрибуты.

| Атрибут | Смысл |
|---|---|
| `stddev` | Среднеквадратичное отклонение итоговой оценки состояния. Это не `sigma` отдельного датчика. |
| `filter_mode` | `warmup` до появления первого пригодного состояния, затем `tracking`. |
| `noise_model_mode` | Что выбрано в YAML: `auto`, `gaussian` или `poisson`. |
| `noise_model` | Какая модель реально используется. В 0.2.1.6 `auto` выбирает `gaussian`. |
| `noise_model_params` | Специфические параметры активной модели шума. Для `gaussian` обычно `{}`. |
| `noise_variance_source` | Источник оценки дисперсии наблюдения. Обычно `per_source_calibration`. |

## Диагностика последнего обновления

Все эти поля относятся **к одному и тому же последнему измерению**:

| Атрибут | Смысл |
|---|---|
| `last_source` | `entity_id` источника последнего байесовского обновления. |
| `measurement_sigma` | Среднеквадратичное отклонение ошибки наблюдения именно для этого измерения. |
| `measurement_variance` | Дисперсия наблюдения `R = measurement_sigma^2`. |
| `innovation` | Разность между скорректированным измерением и прогнозом состояния до обновления. Знак сохраняется. |
| `z_score` | Абсолютная величина инновации, деленная на ее ожидаемое среднеквадратичное отклонение. При расчете учитываются и неопределенность прогноза состояния, и дисперсия измерения. |
| `robust_weight` | Вес измерения после робастной проверки: `1` для согласованного измерения и меньше `1` для сомнительного измерения или выброса. |
| `update_dt_s` | Время между текущим и предыдущим обработанным наблюдением. |

Именно формулировка `z_score` важна: это не "ошибка датчика в сигмах", а нормированная инновация всей модели наблюдения.

# 13. Адаптация во время работы

После начального обучения компонент продолжает медленно адаптироваться:

- `bias` обновляется по робастным межсенсорным остаткам;
- `sigma` уточняется по попарным остаткам измерений, близких по времени;
- `median_dt_s` подстраивается по фактической частоте обновления источника;
- оценка характерного времени периодически пересчитывается фоновой задачей.

Быстрый сенсор не получает искусственно огромный вес только потому, что обновляется чаще: попарные выборки привязываются к более медленному источнику, а эффективное число пар ограничивается.

---

# 14. Поведение при выбросах

Если один сенсор локально уехал относительно остальных, фильтр не выключает его жестко.

Вместо этого:

1. растет `innovation`;
2. растет `z_score`;
3. уменьшается `robust_weight`;
4. влияние конкретного измерения становится меньше;
5. `source_health` показывает, какой именно источник расходится с общей оценкой.

Если источник вернется в согласованный режим, его вес восстановится автоматически.

# 15. Текущее состояние модели шума

Публичный интерфейс разделяет:

```text
noise_model_mode = стратегия выбора модели
noise_model      = реально активная модель
```

В 0.2.1.6:

```text
noise_model_mode: auto
noise_model: gaussian
```

Будущее автоматическое определение пуассоновского шума планируется строить по зависимости дисперсии от среднего уровня:

```text
gaussian: Var(y | mu) ~= const
poisson:  Var(y | mu) ~= k * mu
```

Умножение счетов на коэффициент не создает нового семейства распределений: это по-прежнему `poisson`, а коэффициент относится к масштабу модели наблюдения.

# 16. Ограничения

1. Нет автоматического преобразования единиц.
2. `bias` относительный: без внешнего эталона фильтр не знает общей систематической ошибки всех сенсоров.
3. `sigma` — эффективная ошибка наблюдения, а не паспортная точность датчика.
4. `characteristic_time_s` характеризует наблюдаемую систему целиком, а не обязательно чистую физическую постоянную объекта.
5. Автоматическое определение пуассоновского шума пока не реализовано.
6. Настройка пока только через YAML.
7. Интеграция использует `numpy` и декларирует `numpy>=1.26.0,<3.0.0` в `manifest.json`.

---

# 17. План развития

Планируемые изменения, которые сознательно не включены в 0.2.1.6:

- Config Flow / Options Flow при сохранении совместимости с YAML;
- настоящее `noise_model: auto` с устойчивым выбором между гауссовской и пуассоновской моделями;
- разбиение большого `sensor.py` на отдельные модули истории, диагностики, сохранения состояния и калибровки во время работы;
- интеграционные тесты Home Assistant с имитацией машины состояний и Recorder;
- дополнительная диагностика свежих и устаревших источников.

Внутренние численные параметры вроде минимального веса Student-t, нижней границы ковариации и политики свежести специально не выставлены наружу как пользовательские настройки.

# 18. Совместимость со старыми конфигурациями

Старый экспериментальный параметр:

```yaml
robust_enable: true
```

больше не нужен. Робастное обновление включено постоянно.

`save_every_s` следует размещать внутри `bayes:`:

```yaml
bayes:
  save_every_s: 60
```

Пустой блок допустим:

```yaml
bayes:
```

Его также можно полностью опустить — тогда используются значения по умолчанию.

# 19. Диагностика проблем

## После обновления атрибуты не изменились

Выполните **полный перезапуск Home Assistant**. Перезагрузка YAML не гарантирует перезагрузку Python-модуля пользовательской интеграции.

## `filter_mode: warmup`

Фильтр еще не получил пригодного состояния или не смог восстановить/обучить состояние. Проверьте `ensemble.sources`, состояния исходных сенсоров, Recorder и журнал `bayesian_state_filter`.

## `characteristic_time_status: insufficient_signal`

Это не обязательно ошибка. Если сигнал почти постоянный и движение уровня меньше шума измерения, честный результат — признать `tau` неидентифицируемым.

## `characteristic_time_status: longer_than_history`

История слишком короткая относительно динамики процесса. Увеличьте `history_days`, если это оправдано, либо трактуйте результат как нижнюю границу.

## У одного источника высокий `outlier_rate`

Смотрите одновременно `outliers`, `live_updates`, `last_raw_value`, `last_corrected_value`, `last_innovation`, `last_z_score` и `last_robust_weight`.

`outlier_rate: 1.0` при `2/2` и при `100/100` — статистически совершенно разные ситуации.

# 20. Тесты

Для регрессионных тестов математического ядра Home Assistant не требуется:

```bash
python -m venv .venv
. .venv/bin/activate
pip install -r requirements-dev.txt
pytest -q
```

Тесты проверяют, в частности:

- подавление сильного выброса по Student-t;
- конечность и положительность апостериорной неопределенности;
- калибровку относительных `bias`;
- попарную калибровку `sigma` на асинхронных источниках;
- восстановление известных `sigma` на синтетических данных;
- инвариантность начальной калибровки к порядку исторических точек;
- обработку измерений с временными метками из прошлого;
- воспроизводимость начальной калибровки;
- защиту от ложного схлопывания `sigma` у коррелированного быстрого источника;
- оценку характерного времени на синтетическом процессе Орнштейна—Уленбека.
